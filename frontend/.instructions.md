# Instructions Frontend — Data Fetching

## Règle absolue : TanStack Query pour tout data fetching

Cette application utilise **TanStack Query v5** pour toutes les interactions avec l'API REST.

### OBLIGATOIRE

- Utiliser `useApiQuery` (depuis `src/hooks/useApiQuery.js`) pour **toute lecture** de données API (GET).
- Utiliser `useApiMutation` (depuis `src/hooks/useApiMutation.js`) pour **toute mutation** (POST, PUT, DELETE, PATCH).
- Inclure **toutes les variables de filtre/pagination** dans la `queryKey`.
- Pour toute mutation qui modifie une liste/objet déjà affiché à l'écran, utiliser `optimisticUpdate` (norme du projet). Le hook applique le patch immédiatement, restaure le snapshot si l'API échoue (rollback automatique), puis invalide la queryKey.
- N'utiliser `invalidateKeys` seul que pour des actions sans état affiché (seed, job).

### INTERDIT

- Ne **jamais** utiliser `fetch()` + `useState` + `useEffect` pour charger des données API.
- Ne **jamais** muter `old` dans un `updater` optimiste : retourner une nouvelle référence (spread, `map`, `filter`).
- Ne **jamais** faire de `await fetchData()` manuel après une mutation — l'invalidation TanStack Query s'en charge.

### Conventions

- **queryKeys** : `['domaine', ...parametresVariables]` (ex: `['items', page, category]`)
- **Endpoint dynamique** (avec ID) : utiliser une fonction `endpoint: ({ id }) => '/api/items/' + id`
  - Le body JSON est alors dans `payload.body` : `mutate({ id: 5, body: { name: 'x' } })`
- **Endpoint statique** : `endpoint: '/api/items'`, le payload complet est le body : `mutate({ name: 'x' })`
- **Action sans body** : `mutate(null)` (ex: seed, refresh)

### Référence rapide

```jsx
// Lecture
const listQueryKey = ['items', filter]
const { data, isLoading, error } = useApiQuery({
  queryKey: listQueryKey,
  endpoint: '/api/items',
  params: { category: filter },
})

// Création — optimistic + rollback automatique
const create = useApiMutation({
  endpoint: '/api/items',
  method: 'POST',
  optimisticUpdate: {
    queryKey: listQueryKey,
    updater: (old, payload) => ({
      ...(old || {}),
      items: [
        ...(old?.items || []),
        { id: `__tmp_${Date.now()}`, ...payload, __optimistic: true },
      ],
    }),
  },
})

// Mise à jour
const update = useApiMutation({
  endpoint: ({ id }) => `/api/items/${id}`,
  method: 'PUT',
  optimisticUpdate: {
    queryKey: listQueryKey,
    updater: (old, { id, body }) => ({
      ...(old || {}),
      items: (old?.items || []).map((item) =>
        item.id === id ? { ...item, ...body } : item
      ),
    }),
  },
})

// Suppression
const remove = useApiMutation({
  endpoint: ({ id }) => `/api/items/${id}`,
  method: 'DELETE',
  optimisticUpdate: {
    queryKey: listQueryKey,
    updater: (old, { id }) => ({
      ...(old || {}),
      items: (old?.items || []).filter((item) => item.id !== id),
    }),
  },
})

// Action sans état affiché (seed/job) — simple invalidation
const seed = useApiMutation({
  endpoint: '/api/items/seed',
  method: 'POST',
  invalidateKeys: [['items']],
})
```

## Stack technique

- React 18 + Vite 5
- HUBCSS (design system via `/design-system/current/global.css` link)
- TanStack Query v5 (React Query)
- Lucide React (icônes)
- Authentification via JWT (AuthContext + SSE)
- Pas de React Router (app mono-page)
- Pas d'axios (fetch natif)

## Règles template à respecter

### Versioning et changelog

- La **source de vérité** de la version est [../VERSION](../VERSION).
- Ne pas changer `APP_VERSION` manuellement dans `.env` ou [../.env.example](../.env.example), sauf cas exceptionnel. La valeur est synchronisée depuis [../VERSION](../VERSION).
- Si une évolution du template mérite une nouvelle version, utiliser [../scripts/bump_version.py](../scripts/bump_version.py) ou modifier [../VERSION](../VERSION), puis vérifier la synchronisation.
- Le hook Git installé via [../scripts/install-hooks.sh](../scripts/install-hooks.sh) synchronise automatiquement les versions sur commit. Si les hooks ne sont pas installés, les synchronisations peuvent manquer.
- Toute nouvelle version du template doit avoir une entrée correspondante dans [../CHANGELOG.md](../CHANGELOG.md).
- Le changelog suit **Keep a Changelog** + **Semantic Versioning**. Conserver la structure existante : version datée, sections fonctionnelles, tableau des fichiers modifiés.

### Variables d'environnement et configuration

- Toute nouvelle variable d'environnement doit être ajoutée à [../.env.example](../.env.example).
- Si la variable est consommée côté backend, elle doit être déclarée et typée dans [../backend/config.py](../backend/config.py).
- Si la variable est nécessaire au runtime Docker, elle doit être propagée dans [../docker-compose.yml](../docker-compose.yml).
- Si la variable impacte le frontend au build ou au runtime, vérifier [src/config.js](src/config.js), [src/context/ConfigContext.jsx](src/context/ConfigContext.jsx) et, si besoin, [../docker-compose.yml](../docker-compose.yml).
- Si `FRONTEND_PORT` change, vérifier la règle `FRONTEND_HTTPS_PORT = FRONTEND_PORT + 1` documentée dans [../.env.example](../.env.example) et gérée par `make sync-env` dans [../Makefile](../Makefile).
- Avant de supposer qu'une valeur est librement éditable, vérifier si elle est déjà synchronisée automatiquement par [../scripts/bump_version.py](../scripts/bump_version.py) ou [../Makefile](../Makefile).

### API, schémas et documentation

- Toute modification de contrat API doit être reflétée dans [../docs/API.md](../docs/API.md).
- Toute évolution de payload request/response doit être alignée avec [../backend/schemas.py](../backend/schemas.py).
- Toute nouvelle logique de data fetching frontend doit respecter [../docs/DATA_FETCHING.md](../docs/DATA_FETCHING.md).
- Si une fonctionnalité change le bootstrap ou les URLs exposées au frontend, vérifier [../backend/main.py](../backend/main.py), [src/context/ConfigContext.jsx](src/context/ConfigContext.jsx) et [src/config.js](src/config.js).

## Checklist avant de modifier ou ajouter une fonctionnalité

### 1. Identifier le domaine impacté

- Est-ce un changement **frontend**, **backend**, **API**, **config**, **M2M**, **messages Hub**, **HTTPS/SSE**, **backup/restore**, **tests**, ou **versioning**.
- Lire d'abord les documents et fichiers de référence de la section “Cartographie du projet”.

### 2. Vérifier le contrat de données

- Si la fonctionnalité ajoute ou modifie un endpoint : mettre à jour [../backend/routes](../backend/routes) concerné, [../backend/schemas.py](../backend/schemas.py), puis [../docs/API.md](../docs/API.md).
- Si la fonctionnalité modifie une structure persistée ou un modèle métier : vérifier si une migration SQL est requise dans [../backend/migrations](../backend/migrations).
- Si la fonctionnalité a un impact frontend : vérifier la queryKey, l'invalidation, et la doc [../docs/DATA_FETCHING.md](../docs/DATA_FETCHING.md).

### 3. Vérifier la configuration et les variables d'environnement

- Toute nouvelle variable doit exister dans [../.env.example](../.env.example).
- Si le backend l'utilise, l'ajouter à [../backend/config.py](../backend/config.py).
- Si Docker l'utilise, la propager dans [../docker-compose.yml](../docker-compose.yml).
- Si le frontend en dépend, vérifier [src/config.js](src/config.js), [src/context/ConfigContext.jsx](src/context/ConfigContext.jsx) et le build args du frontend dans [../docker-compose.yml](../docker-compose.yml).
- Si le changement touche les ports frontend, vérifier aussi [../Makefile](../Makefile) et la règle `make sync-env`.

### 4. Vérifier le versioning et le changelog

- Si le template gagne une vraie fonctionnalité, un changement de comportement, ou une correction notable, vérifier s'il faut mettre à jour [../VERSION](../VERSION) et [../CHANGELOG.md](../CHANGELOG.md).
- Ne pas traiter `APP_VERSION` comme source de vérité. La bonne source reste [../VERSION](../VERSION).
- Si une évolution change la documentation ou l'API publique, le changelog doit le refléter.

### 5. Si la fonctionnalité utilise le M2M

- Lire [../docs/REMOTE_APPS.md](../docs/REMOTE_APPS.md) et [../backend/routes/m2m.py](../backend/routes/m2m.py).
- Vérifier si la fonctionnalité dépend de `IS_SHARED` dans [../.env.example](../.env.example) et [../backend/config.py](../backend/config.py).
- Préférer la découverte de services via le Hub plutôt que des URLs hardcodées.
- Si l'UI admin de diagnostic doit évoluer, vérifier [src/components/M2MTests.jsx](src/components/M2MTests.jsx).
- Si le contrat de service discovery ou d'appel inter-app change, mettre à jour [../docs/API.md](../docs/API.md) et éventuellement [../docs/REMOTE_APPS.md](../docs/REMOTE_APPS.md).

### 6. Si la fonctionnalité utilise les messages Hub ou le SSE

- Lire [../docs/HUB_MESSAGES.md](../docs/HUB_MESSAGES.md).
- Ne pas créer un stockage local concurrent pour les messages si le template s'appuie déjà sur le Hub comme source de vérité.
- Les notifications applicatives doivent passer par le backend et le client Hub M2M, pas par un appel direct frontend vers un endpoint M2M sensible.
- Vérifier [src/context/AuthContext.jsx](src/context/AuthContext.jsx), [src/components/MessageBanner.jsx](src/components/MessageBanner.jsx), [src/components/MessageArchive.jsx](src/components/MessageArchive.jsx), et [../backend/routes/tests.py](../backend/routes/tests.py) si le flux de test doit évoluer.
- Si l'application fonctionne en HTTPS, vérifier aussi le proxy `/hub/` et la compatibilité SSE dans [../docs/HTTPS.md](../docs/HTTPS.md), [../nginx.conf](../nginx.conf) et [../nginx-ssl.conf](../nginx-ssl.conf).

### 7. Si la fonctionnalité touche le backup, la base ou les uploads

- Lire [../docs/BACKUP_RESTORE.md](../docs/BACKUP_RESTORE.md).
- Vérifier si les nouvelles données doivent être sauvegardées/restaurées correctement.
- Si une table, colonne ou structure change, ajouter une migration dans [../backend/migrations](../backend/migrations) si nécessaire.
- Si des uploads ou fichiers sont concernés, vérifier le stockage et les volumes Docker dans [../docker-compose.yml](../docker-compose.yml).

### 8. Si la fonctionnalité touche HTTPS, proxy ou URLs

- Lire [../docs/HTTPS.md](../docs/HTTPS.md).
- Vérifier l'impact sur [src/config.js](src/config.js), [src/context/ConfigContext.jsx](src/context/ConfigContext.jsx), [../backend/config.py](../backend/config.py), [../nginx.conf](../nginx.conf), [../nginx-ssl.conf](../nginx-ssl.conf) et [../docker-compose.yml](../docker-compose.yml).
- En HTTPS, privilégier le proxy `/hub/` pour éviter le mixed content et préserver le SSE.

### 9. Vérifier les tests et les écrans de diagnostic

- Si le changement modifie l'API ou l'auth, vérifier les tests backend dans [../backend/tests](../backend/tests).
- Si le changement concerne l'intégration Hub, vérifier aussi [../backend/routes/tests.py](../backend/routes/tests.py), [src/components/EndpointTests.jsx](src/components/EndpointTests.jsx) et [src/components/M2MTests.jsx](src/components/M2MTests.jsx).
- Si le changement introduit une convention frontend réutilisable, s'assurer qu'elle reste alignée avec [../docs/DATA_FETCHING.md](../docs/DATA_FETCHING.md) et ce fichier d'instructions.
